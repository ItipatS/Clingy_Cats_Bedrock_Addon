# Clingy Cats — TODO

Working plan for `feature/hiss-wrongfood` (3 commits ahead of `main` @ `9f51ffe`, not merged). **v1 "done" means:** a player can find a cat, tame it, feed it, pet it, breed it, and watch its mood change — on all 12 breeds, with no locked animation states and no silently-dead systems — and a clean clone of the repo builds with `npm run local-deploy`.

Verify every change with `npm run local-deploy`. Never a bare `npm run build`.

> **Provenance (2026-08-13).** Drafted from a three-way repo audit, then corrected against how the engine actually behaves. Facts confirmed directly against the files: `trust_level` default `0` (`british.json:132`) · `minecraft:tameable` only inside the `wild` group (`:635`) · `sub_state` read nowhere in `RP/` · no `RP/entity/shoulder_anchor.json` · leading space on every `en_US.lang` name line · `trait_curious` resetting `excluded_items` to `[]` (`:1342`).
>
> **Four audit findings were wrong and have been removed — do not let them back in:**
> - *"Still-states lock the cat forever because the group is never removed."* No. `minecraft:behavior.timer_flag_1` is a goal with its own `duration_range`; it ends on duration **or** on interruption by another behavior, and fires `on_end` → `on_idle` either way. A lingering component group means the goal is *available*, not *active*.
> - *"Add `minecraft:tameable` to the tamed group."* Backwards. `tameable` is what *enables* taming; a tamed cat has nothing left to tame, and removing it on tame is correct. The real bug is script-side detection — see the blocker below.
> - *"`take_item: true` on the feed interact is wrong."* It is correct. Feeding takes the item; only the **wrong-food** entry deliberately omits it.
> - *"`despawn` + `persistent` in shared components is dangerous."* Normal. Tamed mobs are despawn-exempt at the engine level, and `minecraft:persistent` means "does not perish when the player quits", not "never despawns".
>
> **Lesson for whoever picks this up:** agents are good at *finding* things in this repo and bad at *judging* whether a Bedrock mechanism is broken. Use them for docs and inventory, not for verdicts on engine behaviour. Anything below still phrased "should"/"would" has not been observed in-game.

## Known bugs

### Ours

- [ ] **Same-tick `getProperty` staleness makes three read-after-write decisions read the pre-write value.** The API docs are explicit: a property set with `setProperty` in the same tick does not read back until the next tick (`node_modules/@minecraft/server/index.d.ts:8848-8867`). Three sites do exactly that:
  - `bond.ts:220` `addTrust(cat, drop)` then `:227` `if (getTrust(cat) >= 300) return;` — the escalation gate reads **pre-drop** trust, not post-drop as the comment at `:182-184` claims. An anxious cat at trust 310 fed rotten flesh (−40 → 270) does not escalate.
  - `bond.ts:170-174` (wild pet) and `interact.ts:93-96` (feed): `addAffection(...)` then `checkAutoTame(...)`, which re-reads via `getAffection` (`bond.ts:69`) — so taming always takes **one extra pet/feed** beyond the documented threshold.
  - `bond.ts:136-137` — same shape in the bond loop.
  Fix: have `addAffection`/`addTrust` return the new value and pass it into `checkAutoTame` / the escalation gate. Low.
- [ ] **Bond-loop trust drift multiplies by nearby player count.** `registerBondLoop` iterates `world.getAllPlayers()` (`bond.ts:101`) and scans a 64-block sphere per player (`:102-106`); the drift at `:110-112` sits above any ownership or distance gate, so a cat inside two players' spheres drifts ±2/s, three players ±3/s. Drift should be a property of the cat, not the audience. (The affection paths below it *are* correctly de-duplicated — tamed bails on `tamedToPlayerId !== player.id` at `:122`, wild is gated by the bonder lock at `:134`.) Same scan also costs O(players × cats). Fix: build a de-duplicated `Set` of cats keyed by entity id, drift once per cat, evaluate per-player logic inside. Low.
- [ ] **Newborn kittens are tamed to an arbitrary nearby player, not the mother's owner.** `pregnancy.ts:92` takes `getPlayers({maxDistance:10})[0]` — results are not distance-sorted — then tames the kitten to them (`:94-97`) with no ownership check. Breeding requires tame, so the mother always *has* an owner; in multiplayer a bystander walks off with the kitten. Contrast `pregnancy.ts:33-38`, `interact.ts:81-83` and `bond.ts:159-161`, which all sort by `distanceSq` correctly. Depends on the tameable fix to look the owner up at all. Same unsorted-`[0]` pattern at `riding.ts:43-44` (anchor spawns on an arbitrary player within 5 blocks, not the interactor). Low.
- [ ] **Petting a sitting/sleeping/grooming cat produces no animation.** `clingy_cats:on_pet` fires `enter_rub_state` directly and its `interact` component has no state filter (`british.json:857`, `:2175-2177`), so `state` becomes `rubbing` while the AC stays parked in `sitting` — the rub never plays and the pet reads as unacknowledged. The AC transition matrix is missing 20 edges overall (sitting→rubbing/hissing/hunting, sleeping→grooming/rubbing/hissing/hunting, rubbing→sitting/sleeping/grooming/hissing/hunting, hunting→sitting/sleeping/grooming/rubbing, walking→hissing); most are unreachable because still states exit through `on_idle` first — this one is not. `RP/animation_controllers/clingy_cats_cat.animation_contollers.json:38-49,51-66,68-83,85-94`. Low.
- [ ] **`clingy_cats:sub_state` is written, synced, and read by nothing — the AC re-rolls the variant client-side.** BP sets it in `on_sleeping` (0/1/2) and `on_grooming` (0/1) (`british.json:2001-2025`) and it's `client_sync: true` (`:29`), but `grep -rn sub_state RP/` returns zero hits. The AC rolls its own `variable.sleep_var = math.floor(math.random(0,3))` / `variable.groom_var`. Two players looking at the same sleeping cat see different poses, and one of 26 property slots is wasted. Fix is one line per branch: `variable.sleep_var` → `q.property('clingy_cats:sub_state')`. `RP/animation_controllers/clingy_cats_cat.animation_contollers.json:52-58,69-75`. Trivial.
- [ ] **`trait_curious` wipes the pickup exclusion list — curious cats will pocket dropped netherite.** Base `minecraft:behavior.pickup_items` (`british.json:384-411`) carefully excludes armor, swords, spears, tridents, shears, spawn eggs, boats, banners, doors, signs, trim materials and sherds; the `clingy_cats:trait_curious` group redefines the component with `"excluded_items": []` and `can_pickup_any_item: true` (`:1337-1348`). `behavior.eat_carried_item` (`:414-417`) only consumes food, so a non-food item sits in the cat's hand until it dies, and `shareables` is `all_items: true` (`:365-373`). If the empty list is deliberate flavour it still needs is_armor/is_sword/is_trident/spawn_egg back in it. Trivial ×13.
- [ ] **Shoulder-anchor ids leak and the 2-anchor cap is trivially bypassable.** `getActiveAnchors` filters live entities within 6 blocks of the player (`riding.ts:20-25`) and `MAX_ANCHORS` is compared against *that* (`:47-48`), so an anchor more than 6 blocks behind stops counting — walk while spamming sneak-interact and you leave a trail of invisible entities. Ids are only pruned in `handleAnchorExpire` (`:67-75`), which needs `findOwnerPlayer` to find the player within 6 blocks of the expiring anchor (`:27-34`); with timers running 8-60s (`BP/entities/cats/shoulder_anchor.json:47-64`) the player has usually moved on, so the JSON list on the player's dynamic property grows without bound. Fix: prune ids whose entity no longer resolves, drop the 6-block filter from the cap check, and store the owner id on the anchor instead of reverse-searching. Low.
- [ ] **`clingy_cats:shoulder_anchor` has no client entity and no localized name.** It's `is_summonable: true` and spawned at runtime by `riding.ts`, but there is no `RP/entity/shoulder_anchor.json` (13 files, none for it) and no `entity.clingy_cats:shoulder_anchor.name` in `RP/texts/en_US.lang`. A BP entity with no client definition produces content-log errors on every spawn and falls back to the raw identifier in any UI that resolves its name. Trivial.
- [ ] **Guide-book grant has no validity guard.** `guideBook.ts:33-34` adds the `clingy_cats:welcomed` tag immediately, then waits 60 ticks before granting (`:35-38`). Disconnect inside that window → `player.getComponent("minecraft:inventory")` throws `InvalidEntityError` in the timeout, and because the tag is already set the player never gets the book on any later login. Guard with `if (!player.isValid) return;` and move `addTag` inside the timeout. Trivial.
- [ ] **Item texture_sets point their MER at a spawn egg in another folder.** `RP/textures/items/meownifier.json:5` and `RP/textures/items/guidebook.json:5` set `metalness_emissive_roughness_subsurface` to `all_black_spawn_egg_mers`, which lives in `textures/items/spawn_eggs/` — texture_set members resolve relative to the JSON's own folder, so neither resolves. This matters because `RP/manifest.json:52-54` declares `"capabilities": ["pbr"]`, putting the pack on the deferred/Vibrant Visuals path where the MER is actually consumed. Even resolved, a spawn egg's metal/roughness layout is wrong data for a magnifying glass and a book. Trivial.
- [ ] **Hunting animation is blended by raw move speed, so a stationary hunting cat snaps to the bind pose.** The AC plays `{ "hunt": "query.modified_move_speed" }` — that value is the *blend weight*, not a speed multiplier. At zero movement the hunt animation contributes nothing and the cat falls back to a flat standing quadruped; the state only exits on `state == 'idle'`, so it holds that stiff pose until the next behavior tick. The unused `hunt_speed` `remap_curve` sitting directly above it (`:109-119`) looks like it was written to solve exactly this and never wired in. `RP/animation_controllers/clingy_cats_cat.animation_contollers.json:121,124-128`. Low.
- [ ] **`eye_index` range is one wider than the eyes array.** Declared `range: [0,33]` (`british.json:130`) but `Array.eyes` holds 33 entries addressed 0..32 (`RP/render_controllers/test.render_controllers.json:203-241`), and the script's real max is `2*11+10 = 32` (3 shapes × 11 colours, `catsbreed.ts:309-327`). Unreachable today; a live out-of-range the moment a 4th shape or 12th colour is added without widening the array. Trivial.
- [ ] **Assignment events only `add`, never remove siblings.** `size_*` / `set_trait_*` / `set_personality_*` are all bare adds (`british.json:1897-1928`). `applyAdultSize` fires `clingy_cats:size_<tier>` on grow-up but `clingy_cats:ageable_grow_up` (`:1816-1826`) removes only `baby` and `visible_baby` — so the grown cat carries **both** `scale_by_age` (from `baby_size_*`, `:435-439`) and `scale` (from `size_*`, `:430-434`). Low ×13.
- [ ] **`.lang` polish:** every one of the 26 name lines in `RP/texts/en_US.lang:5-37` is written `key= Value` — Bedrock does not trim that, so every nameplate and spawn-egg tooltip renders with a leading space. ### Engine bugs — do not re-debug these

- [ ] **`minecraft:behavior.pickup_items` → `on_pickup_item_end` never fires for a stack of exactly 1.** Mojang's bug, already investigated and confirmed: the event is keyed to the item entity, which is destroyed by a full pickup. This is why throw-feeding is built on `minecraft:on_equipment_changed` (`slot.weapon.mainhand`) → `clingy_cats:on_hand_food_gained` → `clingy_cats:on_give` instead. `scripts/logics/throwFeed.ts` holds a polling fallback, deliberately disabled at `scripts/main.ts:22`. **Do not "fix" the pickup path** — the other 12 breeds still carry `on_pickup_item_end -> clingy_cats:on_pick_up` (`british.json:384-386` and equivalents), which is precisely the broken route; the rollout task above replaces it.
